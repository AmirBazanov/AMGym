# Разбор текста через OpenRouter

Файлы: `bot/src/gymbot/llm/openrouter.py` (клиент), `prompts.py` (системный промпт + few-shot), `schemas.py` (`ParseResult`), `handlers/log_text.py` (хендлер с диалогом).

## Поток
сообщение → `build_messages(text, catalog, history)` → `POST {OPENROUTER_BASE_URL}/chat/completions` (`temperature: 0`, `response_format: json_object` если модель не в `_no_json_mode`) → вырезаем первый `{...}` → `ParseResult.model_validate` → предпросмотр в чате → запись только после подтверждения.

### История диалога
`history` — список пар (текст пользователя, JSON результата) из последнего обмена этого пользователя. Вставляется в messages после примеров (EXAMPLES) перед новым текстом, чтобы модель воспринимала его как уточнение. Контекст живёт **15 минут** (CONTEXT_TTL) в памяти; удаляется при нажатии «Сохранить» или «Отмена», и при истечении TTL.

`catalog` — названия упражнений из БД, чтобы модель писала «жим лёжа», а не «жим штанги лёжа на горизонтальной скамье». Сопоставление с `exercises` по `name` и `aliases`; неизвестное упражнение предложи создать, а не создавай молча.

## Бесплатные модели и надёжность
- Список меняется: https://openrouter.ai/models?max_price=0 . Модель задаётся `OPENROUTER_MODEL`, запасные `OPENROUTER_FALLBACK_MODELS` (JSON-список). Суффикс `:free`.
- Лимиты у бесплатных строгие (запросы в минуту и в день). На 429 клиент переходит к следующей модели; не добавляй агрессивных ретраев.
- На 400 с `response_format`: клиент повторяет запрос без `json_object`, результат запоминается в `_no_json_mode` модели.
- Слабые модели путают «3 по 10» (подходы × повторы) и вес. Каждый новый тип ошибки = новый пример в `EXAMPLES` и тест в `bot/tests/test_llm_parse.py`.

## Правка и уточнение
**ParseResult.revises**: флаг true, если ответ исправляет предыдущий, false иначе. Логика в `is_revision()`:
- Если `revises: true` → правка.
- Если `kind == "food"` и **названия продуктов совпадают** (после нормализации, без суффикса `, N шт`) → правка. Пример: «Самса куриная, 1 шт» → «самса куриная, 3 шт» = совпадение нормализованного названия.
- Для `kind == "workout"` только флаг: одно упражнение дважды = новый подход, не правка.

**ParseResult.note**: пояснение модели (было → стало при правке, или почему такая оценка). Показывается в превью отдельным абзацем после списка упражнений или продуктов. Скрывается, если совпадает с текстом пользователя (нормализованное сравнение).

**Правка без чисел**: комментарии о качестве, составе, размере или готовке («плохое качество», «большая самса», «без масла») → модель сама корректирует оценку КБЖУ (примеры в промпте: плохое качество: белок −25%, жир +15%; большая: граммы +30%; без масла: жир −50%) и возвращает полную запись с `revises: true` и `note` (что изменил и почему).

**Логика диалога**: 
- Если новая запись = правка → заменяет старую в превью, её raw_text = цепочка всех текстов («три яйца\nтри штуки»), старая кнопка «Сохранить» перестаёт работать.
- Новая запись и не правка → обе могут быть сохранены, она становится новой историей.
- `kind == "unknown"` (уточняющий вопрос) → следующий ответ продолжает цепь (вплоть до 3 текстов).
- `kind == "question"` (вопрос пользователя) → история не меняется, его ответ не сохраняется.

**Правила в промпте**:
- «N штук» («2 яйца», «три самсы») = N типичных штук: `grams = N × вес одной`, КБЖУ на всё, в `description` добавить `, N шт`.
- Если сообщение уточняет или исправляет → вернуть ПОЛНУЮ исправленную запись с `revises: true`.
- Вопрос о еде или тренировках: `kind="question"`, в `clarification` ответ по существу (2–3 предложения с цифрами, не повторять текст пользователя). Болтовня: `kind="question"` с короткой подсказкой.
- Если непонятно → `kind="unknown"` и уточняющий вопрос в `clarification`.

**Kcal от макросов**: модель часто оценивает kcal неточно. В `ParsedFood` валидатор пересчитывает: `computed = 4 × protein_g + 9 × fat_g + 4 × carbs_g`. Если разница больше 15% от `computed`, kcal заменяется на `round(computed)`. Это позволяет избежать внутренних противоречий (примеры в EXAMPLES).

**Последний пример в EXAMPLES не должен быть записью** (kind ≠ "workout"/"food"), иначе модель путает голое «три штуки» в жизни с правкой примера. Примеры синхронизированы с `tests/test_llm_parse.py` (тест `test_examples_validate`).

## Обработка текста и голоса
`process_text()` в `handlers/log_text.py` — единая точка входа для текста и голосовых сообщений. Принимает:
- `text`: то, что видит модель и диалог (чистый текст или расшифровка голоса).
- `raw_text`: как сохраняется (по умолчанию `text`); голос передаёт `[voice] <расшифровка>`.

При цепочке сообщений каждый текст хранит свою форму, так что corrected by voice «самса\n[voice] три штуки» сохраняется как есть, но модель видит только чистый текст. Пользователь видит над превью «Распознал: «…»».

## Клиент OpenRouterClient
Один экземпляр на процесс (настраивается в Dispatcher как `llm`), переиспользует HTTP-пул и кеш `_no_json_mode` по моделям. Инициализируется через `Settings` (API ключ из `.env`).

## Проверка вживую
```bash
cd bot && uv run python -m gymbot.llm.check "три куриные самсы"
```
Каждый запрос выводит модель и `json_mode=True/False`. Без аргументов — SAMPLES.

Диалог с историей:
```bash
cd bot && uv run python -m gymbot.llm.check --dialog "три куриные самсы" "три штуки"
```
Второе сообщение отправляется с историей первого, как в боте.

## Правка промпта
1. Промпт короткий, по-русски, схема JSON прямо в тексте (`SYSTEM_PROMPT`).
2. Каждый пример в `EXAMPLES` обязан проходить `ParseResult` (тест `test_examples_validate`).
3. Примеры синхронизированы с `bot/tests/test_llm_parse.py`.
4. КБЖУ от модели — оценка (`FoodEntry.estimated = True`); если не указан вес, берётся типичная порция. Показывай пользователю, что это оценка.

Никогда не отправляй в OpenRouter токен бота, id пользователей или что-то кроме текста сообщения и каталога упражнений.
