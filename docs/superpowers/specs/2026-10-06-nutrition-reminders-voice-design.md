## 1. Питание в мини-аппе

### Цель
Новая вкладка «Питание» с переключателем «День / Неделя / Настройки». «День»: что съедено за день, итог КБЖУ, сколько осталось до нормы, удаление записи. «Неделя»: ккал и БЖУ по дням против нормы. «Настройки»: норма КБЖУ и напоминания (п.2).

Вкладка «Сегодня» уже занята тренировкой дня, поэтому питание идёт пятой вкладкой: «Сегодня · Программа · История · Прогресс · Питание». Нужно проверить, что пять вкладок помещаются в `tabbar` на узком экране (360 px).

### Что есть сейчас
- `FoodEntry` (`bot/src/gymbot/db/models.py`): `eaten_at` — `DateTime(timezone=True)`, UTC, с индексом; `description`, `grams`, `kcal`, `protein_g`, `fat_g`, `carbs_g` (Numeric), `estimated`, `raw_text`. Полей `source` и `client_id` нет, и для удаления они не нужны.
- Ошибка: `log_text._save` не передаёт `eaten_at`, поэтому туда пишется `utcnow` в момент нажатия «Сохранить», а не время отправки сообщения. Тренировки берут `pending.sent_at`. Еда, отправленная в 23:58 и подтверждённая в 00:01, попадёт на следующий день. Исправление — одна строка `eaten_at=pending.sent_at`, делается после слияния работы другого агента.
- `User` уже содержит `kcal_target` и `protein_target_g`. Полей для жиров и углеводов нет.
- `/undo` удаляет только подходы. Еду из чата сейчас удалить нельзя; удаление в мини-аппе закрывает этот пробел.

### Решение: где хранить норму
Поля в `User`, отдельная таблица профиля не нужна: пользователь один, норма одна, `rest_seconds` хранится так же. Задаётся только в мини-аппе. Команду бота пока не делаем. Историю изменения нормы не храним; «Неделя» сравнивает все дни с текущей нормой (см. риски).

### Схема БД — миграция `0002_nutrition_targets`
- `users.fat_target_g` Integer, nullable.
- `users.carbs_target_g` Integer, nullable.
- Через `batch_alter_table` (SQLite), с downgrade. Проверка: `alembic upgrade head && alembic downgrade -1 && alembic upgrade head`.

### Границы дня
Сервер — единственный источник истины о том, какой сейчас день. Локальная полночь в `TIMEZONE` и следующая полночь переводятся в UTC в Python, и записи фильтруются по `eaten_at >= start AND eaten_at < end`. Так используется индекс, и одинаково работает на SQLite и Postgres. `func.date(eaten_at)` не использовать: он группирует по UTC-дате и ведёт себя по-разному в разных диалектах. При чтении время проходит через `_aware()`, потому что SQLite теряет смещение. Неделя — это 7 таких диапазонов, либо один запрос на 7 дней с раскладкой по локальной дате в Python.

### API-контракт
Все числа в JSON — `float`, `Decimal` явно приводится к `float`: pydantic v2 отдаёт `Decimal` строкой. Ключи в camelCase, как в существующем API. Норма `null` означает «не задана».

`GET /api/nutrition/day?date=YYYY-MM-DD` — параметр необязателен, по умолчанию сегодня в `TIMEZONE`.
```json
{
  "date": "2026-10-06",
  "targets": {"kcal": 2600, "protein": 160, "fat": 80, "carbs": 300},
  "totals":  {"kcal": 1840.0, "protein": 112.0, "fat": 61.0, "carbs": 190.0},
  "remaining": {"kcal": 760.0, "protein": 48.0, "fat": 19.0, "carbs": 110.0},
  "entries": [
    {"id": 17, "eatenAt": "2026-10-06T09:12:00Z", "time": "12:12",
     "description": "гречка", "grams": 200.0, "kcal": 220.0,
     "protein": 8.0, "fat": 2.0, "carbs": 42.0, "estimated": true}
  ]
}
```
`remaining[x] = targets[x] - totals[x]`. Значение может быть отрицательным (перебор) и равно `null`, если норма не задана. `time` — локальное время в `TIMEZONE`, чтобы телефон в другой зоне не показывал другое время. Записи отсортированы по `eatenAt`.

`GET /api/nutrition/week?end=YYYY-MM-DD` — 7 дней, последний из них `end`; по умолчанию `end` = сегодня.
```json
{
  "targets": {"kcal": 2600, "protein": 160, "fat": 80, "carbs": 300},
  "days": [
    {"date": "2026-09-30", "kcal": 2410.0, "protein": 150.0, "fat": 70.0, "carbs": 280.0, "entries": 5}
  ]
}
```
Дни без записей тоже приходят, с нулями и `entries: 0`.

`DELETE /api/food/{id}` возвращает 204, или 404, если запись не найдена либо принадлежит другому пользователю.

Норма задаётся через существующий `PUT /api/settings`: в `SettingsIn` добавляется `targets: {kcal?, protein?, fat?, carbs?}`. Допустимые значения: kcal 0..10000, граммы 0..1000, `null` сбрасывает норму. `StateOut` получает поле `targets`. Новый эндпоинт не нужен.

Правку записи (`PATCH /api/food/{id}`) пока не делаем.

### Экраны
- **День.** Стрелки «← дата →», нельзя уйти дальше сегодня. Четыре полосы прогресса (ккал, Б, Ж, У) с подписью «1840 / 2600, осталось 760» или «перебор 120». Ниже список записей: время, описание, граммы, ккал и БЖУ. Удаление идёт через `confirm()`, как удаление тренировки в «Истории». Если записей нет: «Пиши еду в чат боту: «200 г гречки и 2 яйца»». Если норма не задана, полос нет, только итог и ссылка «Задать норму».
- **Неделя.** Столбцы ккал по дням (`BarSeries`) с горизонтальной линией нормы, ниже таблица по дням: ккал, Б, Ж, У. Подписи осей с единицами.
- **Настройки.** Четыре поля `NumField` для нормы и блок напоминаний (п.2).
- Данные о еде не попадают в офлайн-хранилище `store.ts`. Экран загружает их с сервера при открытии. В демо-режиме вне Telegram — пустое состояние с пояснением. Типы ответов лежат в `miniapp/src/api.ts`.

### Риски
- Если строку `eaten_at` в `log_text` не исправить, записи около полуночи окажутся не в том дне.
- Норма, изменённая в середине недели, пересчитает все прошлые дни недели. Для одного пользователя это приемлемо, таблица истории норм пока не нужна.
- Пять вкладок могут не поместиться: подписи придётся сократить.

### Критерии готовности
- Миграция `0002` проходит upgrade, downgrade и снова upgrade.
- Еда, записанная из чата в 23:58 по `TIMEZONE` (и подтверждённая после полуночи), попадает в тот день, когда сообщение было отправлено.
- Тесты `day` и `week` на SQLite проходят, включая границу дня по `TIMEZONE`: 00:30 МСК — это 21:30 UTC предыдущего дня.
- `DELETE` чужой записи возвращает 404.
- В JSON числа, а не строки.
- Проверки из CLAUDE.md зелёные: `ruff`, `pytest`, `typecheck`, `build`.

### Делегировать (п.1)

Контракт из этого раздела, числа — float.

## 3. Голосовые сообщения

### Цель
Пользователь отправляет голосовое сообщение. Бот распознаёт речь и показывает «Распознал: «…»». Дальше всё как для текста: разбор, предпросмотр, «Сохранить». В `raw_text` пишется транскрипт с пометкой голоса.

### Варианты распознавания
Сведения проверены 2026-10-06 по первоисточникам. Что не удалось подтвердить, помечено «не проверено».

| | Цена | Русский | Задержка | Эксплуатация | Голос уходит | Маленький VPS |
|---|---|---|---|---|---|---|
| **Groq `whisper-large-v3-turbo`** | бесплатный тариф: 20 запросов/мин, 2000 запросов/сутки, 7200 с аудио/ч, 28 800 с/сутки | класс large-v3 | ~1–2 с (не проверено) | отдельный ключ Groq, HTTP | в Groq | да, нагрузки ноль |
| OpenRouter STT (`openai/whisper-large-v3-turbo`) | платно, копейки за секунду аудио; бесплатных STT-моделей нет | класс large-v3 | не проверено | тот же ключ OpenRouter | в OpenRouter и провайдеру | да |
| OpenRouter, бесплатные омни-модели с аудио (`*:free`, 3 шт.) | 0 | не проверено | не проверено | это чат-модели, а не STT; лимиты и состав `:free` часто меняются | провайдеру | да |
| Локальный `faster-whisper` small int8 | 0 | WER 11.4 на FLEURS-ru (у medium 7.2, у large-v2 5.6) | 8–20 с на клип 15 с при 1–2 vCPU (оценка, не проверено) | веса ~0.5 ГБ, ~1.5 ГБ RAM, пакеты ~100–150 МБ; системный ffmpeg не нужен (PyAV) | никуда | впритык; medium и large не влезают |

Источники:
- Groq: console.groq.com/docs/speech-to-text, console.groq.com/docs/rate-limits.
- OpenRouter: openrouter.ai/docs/guides/overview/multimodal/stt, список моделей `/api/v1/models`.
- faster-whisper: github.com/SYSTRAN/faster-whisper.
- WER: статья Whisper, arXiv 2212.04356, табл. 13.

Подробности:
- **Groq.** Эндпоинт OpenAI-совместимый: `https://api.groq.com/openai/v1/audio/transcriptions`, multipart. Принимает `ogg`, файл до 25 МБ на бесплатном тарифе, параметр `language=ru`. Минимальная тарифицируемая длина — 10 с. На бесплатном тарифе это влияет только на учёт лимита. Ogg с Opus внутри отдельно не проверялся: проверить на настоящем голосовом из Telegram.
- **OpenRouter.** Есть `/api/v1/audio/transcriptions`, тоже принимает multipart. Значит, тот же клиент переключается на OpenRouter сменой `STT_BASE_URL`, `STT_MODEL` и `STT_API_KEY` без нового кода, но это не проверено.

**Рекомендация: Groq `whisper-large-v3-turbo`.**
- Бесплатно, с большим запасом: 50 сообщений по 60 с — это 3000 с при лимите 28 800 с в сутки.
- Лучшее качество русского из бесплатных вариантов.
- Сервер не нагружается, что важно для маленького VPS.

Запасные варианты:
- OpenRouter whisper — копейки, переключается через `.env`.
- Локальный faster-whisper в план не входит. Он заметно хуже по качеству и тяжёлый для VPS. Вернуться к нему, только если пользователь не хочет отдавать голос внешнему сервису.

### Интеграция
- `Settings` (`bot/src/gymbot/config.py`):
  - `stt_api_key: str = ""`
  - `stt_base_url: str = "https://api.groq.com/openai/v1"`
  - `stt_model: str = "whisper-large-v3-turbo"`
  - `stt_max_seconds: int = 120`
- В `.env.example` — `STT_API_KEY=` пустым, остальные значения закомментированы, с подсказкой, где взять ключ (console.groq.com). Ключ не логируется.
- `bot/src/gymbot/stt.py`: `async def transcribe(audio: bytes, filename: str, settings) -> str`. Это `multipart` POST через `httpx` (уже в зависимостях) на OpenAI-совместимый `/audio/transcriptions` с `language=ru`. Таймаут 30 с, при ошибке — `STTError`. Отдельный SDK не нужен.
- `bot/src/gymbot/handlers/voice.py`: `@router.message(F.voice)`.
  1. Если `stt_api_key` пуст, ответить «Голос не настроен: нужен ключ распознавания в .env».
  2. Если `voice.duration > stt_max_seconds`, ответить «Слишком длинное, до 2 минут».
  3. Показать `send_chat_action("typing")`.
  4. Скачать файл: `await bot.download(message.voice)` возвращает `BytesIO`. Telegram отдаёт ботам файлы до 20 МБ, голосу этого хватает.
  5. Вызвать `transcribe(..., filename="voice.ogg")`.
  6. Пустой транскрипт → «Не расслышал, попробуй ещё раз».
  7. Иначе — `process_text(message, transcript, raw_text=f"[voice] {transcript}", prefix=f"Распознал: «{transcript}»\n\n")`.
- Роутер подключается в `bot/src/gymbot/main.py` до `log_text.router`. Фильтр `F.voice` с текстовым не пересекается, но порядок держим явный.
- **Изменение в `log_text.py`, только после слияния работы другого агента.** Из `log_free_text` вынести `async def process_text(message, text, settings, sessionmaker, *, raw_text: str | None = None, prefix: str = "")`. Разбор, `PENDING`, предпросмотр и клавиатура переезжают в неё, а `log_free_text` её вызывает. В LLM уходит чистый транскрипт, пометка `[voice]` попадает только в `raw_text`. Если контекст диалога у другого агента хранится по сообщениям, транскрипт должен попадать туда как обычный текст. `/undo` группирует подходы по совпадению `raw_text`, и одинаковая пометка у всех подходов одного сообщения это не ломает.
- В `HELP` (`handlers/common.py`) добавить строку «Можно голосом».

### Риски
- Распознавание путает числа («три по десять на шестьдесят» вместо «3×10 по 60»). Это смягчается тем, что пользователь видит транскрипт и предпросмотр до сохранения, а LLM-разбор переваривает числа словами. Это нужно проверить на живых примерах.
- Бесплатный тариф внешнего сервиса могут урезать. Тогда нужен понятный ответ при 429 и запасной вариант (см. сравнение).
- Голос уходит внешнему сервису. Для личного дневника тренировок это приемлемо, но пользователь должен это знать.
- Конфликт с работой другого агента в `log_text.py`. Вынос `process_text` делается строго после его слияния.

### Критерии готовности
- Голосовое «жим лёжа три подхода по десять на шестьдесят» показывает транскрипт и предпросмотр. После «Сохранить» подходы записаны с `raw_text`, который начинается с `[voice] `.
- Без ключа — понятный ответ, без падения.
- Тест `stt.transcribe` с подменённым `httpx` (`MockTransport`): форма запроса (`model`, `language=ru`, файл), разбор ответа, ошибка 429/5xx превращается в `STTError`. Тест хендлера с подменёнными `transcribe` и `process_text`.
- Ключ не появляется в логах и исключениях.

### Делегировать (п.3)
- bot-backend: `bot/src/gymbot/stt.py` и `Settings`/`.env.example` (STT_*). Можно начинать сразу, это не зависит от `log_text`.
- bot-backend (после слияния работы другого агента): вынести `process_text` в `log_text.py`, `bot/src/gymbot/handlers/voice.py`, подключение в `main.py`, строка в `HELP`.
- test-writer: `bot/tests/test_stt.py` (`httpx.MockTransport`) и `bot/tests/test_voice_handler.py` (подмена `transcribe` и `process_text`, проверка префикса «Распознал» и `raw_text`).

## 2. Напоминания

### Цель
Бот в заданное локальное время присылает «Креатин», «Протеин» или «Добей КБЖУ: осталось X ккал / Y г белка». Последнее считается через `day_summary` из п.1. Напоминание не уходит дважды и не теряется при перезапуске в ту же минуту.

### Схема БД — миграция `0003_reminders` (`down_revision = "0002"`)
Таблица `reminders`:

| Поле | Тип | Смысл |
|---|---|---|
| `id` | Integer PK | |
| `user_id` | FK `users.id`, `ondelete=CASCADE`, index | |
| `minute_of_day` | Integer, 0..1439 | локальное время в `TIMEZONE` (09:30 → 570) |
| `kind` | String(16) | `text` или `nutrition` |
| `text` | Text, nullable | для `text` — что прислать; для `nutrition` не используется |
| `enabled` | Boolean, default true | |
| `last_sent_on` | Date, nullable | локальная дата последней отправки, для защиты от дублей |
| `created_at` | DateTime(tz) | |

Используются только переносимые типы. `minute_of_day` вместо `Time` выбран потому, что так проще сравнивать и нет разницы в хранении `Time` между SQLite и Postgres. Дни недели пока не поддерживаются: напоминания ежедневные.

### Планировщик: свой цикл на asyncio, без APScheduler
Почему не APScheduler: это новая зависимость. Задания в памяти теряются при перезапуске, а постоянное хранилище в 3.x синхронное и хранит задания через pickle; 4.x до сих пор не стабилен. Защиту от дублей всё равно пришлось бы писать самим. Состояние в БД плюс цикл в 30 строк проще и одинаково работает на SQLite и Postgres.

`bot/src/gymbot/services/reminders.py`:
- `async def tick(session, bot, now_utc, tz) -> int` — одна проверка, возвращает число отправленных. Время передаётся параметром, чтобы тесты не спали.
- Напоминание пора отправлять, если `enabled`, `due <= now_local < due + GRACE` (GRACE = 30 мин), где `due` — сегодня в `minute_of_day` по `TIMEZONE`, и `last_sent_on IS NULL OR last_sent_on < today_local`.
- **Захват до отправки:** `UPDATE reminders SET last_sent_on = :today WHERE id = :id AND (last_sent_on IS NULL OR last_sent_on < :today)`, коммит. Отправляем, только если `rowcount == 1`. Это атомарно на SQLite и Postgres и защищает от дублей даже при двух запущенных процессах.
- Если отправка не удалась (сеть, `TelegramRetryAfter`), `last_sent_on` возвращается к старому значению, и следующая проверка в пределах GRACE повторит попытку.
- Семантика — «не больше одного раза». Если процесс упадёт между захватом и отправкой, это напоминание за день пропадёт; это осознанный выбор. Перезапуск в ту же минуту не теряет напоминание: после старта проверка увидит его в окне GRACE.
- Если напоминание создано или его время изменено на уже прошедшее сегодня, ставится `last_sent_on = today`. Иначе оно сработает сразу, а не со следующего дня.
- Цикл в `main.run()`: `asyncio.create_task(reminder_loop(...))` рядом с `polling`, только при `run_bot`. Проверка раз в 30 с, каждая обёрнута в `try/except` с логом, чтобы ошибка одной проверки не убила цикл. При остановке задача отменяется в `shutdown`.
- Получатель — `user.telegram_id`: личный чат совпадает с id пользователя. Если бот заблокирован (`TelegramForbiddenError`), это логируется, `last_sent_on` остаётся.

Тексты:
- `text`: сам текст, например «Креатин».
- `nutrition`: «Добей КБЖУ: осталось 760 ккал / 48 г белка». Если норма выполнена — «КБЖУ на сегодня закрыт». Если норма не задана — «Норма КБЖУ не задана, задай её в дневнике → Питание → Настройки». Под сообщением кнопка WebApp «Открыть питание», если задан `MINIAPP_URL`.

### API-контракт
```
GET    /api/reminders          -> [Reminder]
POST   /api/reminders          {time, kind, text?, enabled?} -> Reminder (201)
PATCH  /api/reminders/{id}     {time?, kind?, text?, enabled?} -> Reminder
DELETE /api/reminders/{id}     -> 204
Reminder = {"id": 3, "time": "09:30", "kind": "text", "text": "Креатин", "enabled": true}
```
Валидация: `time` должен соответствовать `^([01]\d|2[0-3]):[0-5]\d$` и переводится в `minute_of_day` на сервере. Для `kind=text` `text` обязателен, 1..200 символов. Не больше 20 напоминаний на пользователя. Чужой `id` даёт 404.

### Управление
Только мини-апп, вкладка «Питание → Настройки», блок «Напоминания». Список: время, текст или «Сводка КБЖУ», переключатель вкл/выкл. Кнопка «Добавить» открывает `Sheet` с полем времени (`<input type="time">`), типом (Текст / Сводка КБЖУ) и текстом. Удаление через `confirm()`. Команды бота не делаем: для списка и переключения пришлось бы строить инлайн-клавиатуры, а это больше кода, чем экран.

### Риски
- Процесс бота на домашнем ПК или в WSL выключен — напоминаний нет. Это лечится только VPS.
- При `RUN_BOT=false` напоминания не работают, и это ожидаемо.
- На Postgres `rowcount` у `UPDATE` через async-драйвер работает. Нужно проверить на asyncpg при переезде.

### Критерии готовности
- Миграция `0003` проходит upgrade, downgrade и снова upgrade.
- Тесты `tick` с подменённым `bot` и временем:
  - отправка в `due`;
  - повторный `tick` в ту же минуту не шлёт второй раз;
  - «перезапуск» (новый вызов с тем же состоянием БД) в пределах GRACE шлёт один раз;
  - после GRACE не шлёт;
  - выключенное напоминание не шлёт;
  - созданное на прошедшее время сегодня не шлёт до завтра;
  - ошибка отправки откатывает `last_sent_on`;
  - текст `nutrition` с нормой, без нормы и при перевыполнении.
- Живая проверка: напоминание на текущее время + 1 мин приходит один раз.

### Делегировать (п.2)
- bot-backend: миграция `0003` и модель `Reminder`; `bot/src/gymbot/services/reminders.py` (`tick`, `reminder_loop`, тексты, переиспользование `nutrition.day_summary`); CRUD `/api/reminders` в `api/app.py`; запуск и остановка цикла в `main.py`.
- test-writer: `bot/tests/test_reminders.py` по критериям выше (подменённый `bot.send_message`, время через параметр) и `bot/tests/test_api.py`: CRUD, валидация `time`, чужой `id`.
- miniapp-frontend: блок «Напоминания» во вкладке «Питание → Настройки», `Sheet` добавления и правки, типы в `api.ts`.

## 4. История и графики: что есть и что может быть непонятно

### Что есть сейчас
- **История** (`miniapp/src/screens/History.tsx`). Заголовок «За 30 дней», три плитки: тренировки, подходы, тоннаж за 30 дней. Ниже — весь список тренировок, сгруппированный по «Неделя N» программы. В карточке дата, число упражнений, подходов, тоннаж, длительность. В раскрытой карточке — подходы «вес × повторы» и кнопка удаления.
- **Прогресс** (`miniapp/src/screens/Progress.tsx`). Выпадающий список упражнений, период «4 нед / 8 нед / Всё», плитки «макс. вес», «оценка 1ПМ», «рост 1ПМ %». Переключатель «Вес / 1ПМ / Объём» над линейным графиком по тренировкам. Таблица последних шести точек. Столбцы «Тоннаж по неделям, все упражнения» по неделям программы.

### Гипотезы (по коду)
1. **Номера недель скачут.** Тренировки из чата не привязаны к дню программы. Номер недели им считается от *текущей* даты старта и зажимается в диапазон 1..N (`program_position`). При смене даты старта старые тренировки перенумеровываются. Тренировки до старта попадают в «Неделю 1». Два прохода программы дают две группы «Неделя 1». В «Прогрессе» подписи «Н1…» тоже берутся из программы, а не из календаря.
2. **«За 30 дней» относится только к плиткам**, а список под ними содержит всю историю.
3. **Нужного упражнения нет в списке «Прогресса».** Список строится только из упражнений *текущей программы*, которые уже выполнялись. Упражнение, записанное из чата под названием, которое дал LLM, или не входящее в программу, на графики не попадает.
4. **Подписи метрик неточные.** «Рабочий вес» — это на деле максимальный вес за тренировку. «1ПМ» — расчёт по формуле Эпли, и это нигде не объяснено. «Рост 1ПМ» сравнивает первую и последнюю точку выбранного периода. «Объём» показан в кг, а «Тоннаж» — в т, хотя это одна и та же величина. У осей нет единиц, и ось Y начинается не с нуля, поэтому небольшие изменения выглядят как большие скачки.
5. **Подходы без веса и дропы.** Подходы с собственным весом показываются как «0 × 12» и не попадают на графики. Дропы из чата (`drop_index > 0`) не показываются совсем: сервер сворачивает их в основной подход.
